# 开发交付编排 (Dev Delivery)

核心原则：**写手唯一、审查独立且只读、验收 fail-closed、修复只回写手**。
多 agent 抬的是下限（靠闸门），上限仍由主模型决定——所以闸门要真、要短、要有证据。

## 0. 判断档位

- **全流程**：多文件 / 会交付给用户运行 / 涉及数据或安全的改动。
- **精简版**：单文件小工具、探索性脚本 → 主会话先列验收点 → 实现时自测覆盖 →（可选）派 reviewer 静态审查一遍。

## 1. HITL 计划门（大改动才要）

花预算之前先出 3-5 行计划：动哪些文件、模块边界/契约、失败模式、验收方式。让用户点头再开工——返工一张计划表，远比返工一坨代码便宜。

## 2. QA-first：先冻验收清单

派 **reviewer**（只读）产出验收清单：编号 + 每条的通过线 + 严重级别 P0-P3。
清单**冻结后**才写代码；中途改需求 = 改清单并说明。

## 3. 单写手实现

派 **worker-coder**，一次派一个模块。"写手唯一"是**每条工作流内部**的规则，不是整个项目只有一个写手——互相独立的工作流可以并行（见下）。

- **verification-before-completion**：改完必须自己先运行验证（测试/命令输出）再回报；没有新鲜运行输出，不许说"完成"。
- **每条工作流声明一句"读退出码"的验证命令**——一条退出码能裁决该工作流通过/失败的命令（测试套件、构建、lint、脚本）。写手运行它并引用「命令 + 退出码」；主会话在验收时重跑。子代理*报告*"测试通过了"是声明，不是证据——退出码才是证据。（这就是 world.run 的教训：判断交给命令的退出码，不交给模型的自我汇报。）
- **每张派单声明文件边界**——写手允许触碰的路径/glob 清单。验收时主会话跑边界闸门：`node <pack-root>/tools/gates/boundary-check.mjs --boundary <patterns> --git-base <base-ref>`（必须 exit 0）。越界改动即使代码本身完美也是 P0——它意味着两个写手即将相撞。
- 回报格式：全包统一的五段报告契约（`REPORT-CONTRACT.md`）——改动文件清单 + **已验证**段放运行证据（每条=命令+退出码）+ 遗留风险按 **未覆盖/已跳过** 分开写。

### 并行工作流（多模块任务）

两个模块的文件集合互不相交时，就是两条独立工作流。此时**在同一条消息里**并行派 N 个 worker-coder，每个带上自己那份冻结清单。

| 可以并行 | 要并成一条工作流 |
|---|---|
| 不同目录 / 模块 / 项目 | 同一个文件（入口、路由、注册表、`package.json`、lockfile） |
| 接口冻结后的不同服务边界 | 数据库 schema / 迁移 |
| 文档与代码，且在不同文件 | 共享的 i18n / 配置文件 |

规则：

1. **先冻接口再派单**——函数签名、数据结构、文件路径写进每张派单里。接口动了，并行就变返工。
2. **再冻每条工作流的文件边界**——写手可触碰的路径/glob 清单，随派单一起记录。合并后证明边界守住了：`node <pack-root>/tools/gates/boundary-check.mjs --boundary <patterns> --git-base <merge-base>` 必须 exit 0。
3. 必须改的共享文件**自成一个工作流**：主会话（或一个写手）先落它，其余写手基于结果开工。
4. 每条工作流**走完全同一套流程**：QA-first 清单切片 → 写手自验证 → 只喂 diff 的独立审查 → fail-closed 验收。并行改变的是*几个写手同时在跑*，不是*每个人怎么被闸*。
5. **集成归主会话**：合并、跑跨模块检查、在集成后的树上把每条工作流的验收项重跑一遍（含那句退出码验证命令和边界闸门）——单条工作流的审查看不见跨模块的破坏。

## 4. 独立只读审查

派 **reviewer** 审查。派单要点：

- **只喂 diff + 需求（+ 可选提交 SHA），不喂会话历史**——保证干净视角、防止被写手的思路带走。
- 输出：每条 = 位置（文件:行号）+ 现象 + 级别（P0-P3）；禁止无证据的泛泛建议。
- **finder ≠ fixer**：审查者只找不修；修复一律回唯一写手；**单轮修复，不递归**。

## 5. fail-closed 验收

- **unknown = fail**：无法确认的项按"未通过"处理，除非显式豁免并写明理由。
- 空 diff 需要显式豁免才能算"无需改动"。
- 数字类断言必须能追到一手输出（测试日志/命令输出），不接受"我跑过了"。
- **验收时机械闸门全部跑一遍**（都必须 exit 0）：
  - `node <pack-root>/tools/gates/boundary-check.mjs --boundary <patterns> --git-base <base>` —— 没有任何越界文件被改动。
  - `node <pack-root>/tools/gates/report-lint.mjs <写手报告.md>` —— 写手报告符合五段契约（且没有把"跳过"伪装成"被挡"）。
  - 该工作流声明的那句**退出码验证命令**。

## 6. 视觉闸门（交付物是 UI / 网页 / PPT 时追加）

- 渲染 → 截图 → 判卷（pass/fail + 证据，每页/每屏一行）→ 修 → 重渲染重判。
- 判卷派 **visual-judge**（零写权限，只看渲染图，不看源文件）。
- 机械闸门（可选）：改了 UI 文件但整轮没有任何截图证据 → 收尾时自动弹回补证据。示例 hook 见本仓库 `hooks/ui-screenshot-gate.mjs`。

## 7. 失败处理——先归因，再行动

「重派一次」不是一条规则。三类失败的正确动作互相相反：

- **`failed-transport`**（超时、10 分钟无输出被杀、Turn execution failed、供应商 4xx/5xx）：重试归宿主/供应商层管。不要烧协议重试——等待，然后经留账再查。记 `mark --status failed-transport`。
- **`failed-protocol`**（agent 产出不成形、不遵守契约、越界改文件、无证据宣称完成）：缩小范围**重派一次**；第二次还是协议失败，说明问题在 brief → 按 `failed-definition` 处理。
- **`failed-definition`**（任务本身派错了——范围不对、和工作流重复、按现写法不可达）：**绝不原样重派。**作废该任务，作废所有依赖它的成果，重新立单。
- **熔断**：同一通道/模型**连续 2 次**失败 → 换通道/换模型，不再打第三次。
- **防静默换模型**：对第三方 OpenAI 兼容端点，校验响应里的 `model` 字段与请求一致（`scripts/verify-model.mjs`）——有的端点对不认识的模型名会静默改用默认模型应答。
- 每个结局都用 `tools/ledger/dispatch-ledger.mjs` 落账——不落账的失败等于静默失败。

## 8. 派发留账（多次派发就建议开）

- 机械账本：`node <pack-root>/tools/ledger/dispatch-ledger.mjs append|mark|status` —— 追加式 JSONL，位于 `<project>/.dispatch/ledger.jsonl`（首次使用自动创建，自带 `.gitignore`）。每条事件携带任务 id、lane、模型、不变量 brief 与参数块的 sha256、输出路径、时间戳和状态（`dispatched` / `succeeded` / `failed-transport` / `failed-protocol` / `failed-definition` / `verified` / `completed` / `voided`）。
- `status` 回答「哪些结论还没验证」——缺口清单从账本里读出来，不靠脑子记。
- 散文层（可选，不变）：任务全文 + 原始输出存 `<project>/.dispatch/<时间>-<角色>.md`；多轮进度写 `.dispatch/STATE.md`。

## 交付前自检（逐条过）

- 验收清单逐条核过？未过的项有没有显式豁免并写明理由？
- 审查发现的问题都有位置+证据？P0/P1 全部修掉或写明为什么不修？
- 写手声明"完成"之前，有没有新鲜的运行输出？
- 视觉类交付：有没有截图证据 + 判卷结论？
- 派发留痕齐吗（若开了）？
